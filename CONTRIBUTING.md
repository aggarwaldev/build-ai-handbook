# Contributing to the Build AI handbook

The book and its labs are open: anyone can report a problem or propose a change. This guide
says what helps most, how the repository is laid out, how to check a change before you send
it, and how the book is written.

## What helps most

- **Fixing mistakes.** A wrong number, formula, explanation, link or command. Small fixes
  can go straight to a pull request.
- **Reporting problems.** If you find a mistake but not the fix, or a lab that fails, open
  an issue at <https://github.com/aggarwaldev/build-ai-handbook/issues>. Choose "Mistake in
  the book" or "A lab does not work"; each form asks for what is needed to reproduce it.
- **Improving a lab or its tests.** Clearer code, a missing test, or a step that does not
  match what its page says.
- **Proposing a chapter or a lab.** Open a "Suggest a chapter, lab or improvement" issue
  first, so the scope is agreed before anyone writes it. A new page changes the reading
  order, the contents and the search index, and chapter numbers appear in the text, so
  where it goes matters as much as what it says.

## Quick fixes in the browser

Every page of the book ends with an "Edit this page" link to its file on GitHub. Use it for
a typo, a broken link or a wrong sentence:

1. Follow the link. If you cannot write to the repository, GitHub offers to fork it for you.
2. Edit the text in GitHub's editor. Change the words, not the HTML tags around them.
3. Commit the change with a short description of what was wrong. GitHub then offers to
   open a pull request with it.

GitHub's web editor (the pencil icon on any file) works the same way for files outside
`book/`. The checks run on your pull request; if one fails, its log says what is wrong
and where.

## How the repository is laid out

| Path | What it holds |
| --- | --- |
| `book/` | Every page of the book, one HTML file per chapter, lab or reference page. This folder is the whole website |
| `book/assets/handbook.js` | Its `BOOK` list sets the reading order: the sidebar, the previous and next links, search and the progress tracker all follow it |
| `book/assets/widgets/` | One script per interactive widget |
| `book/assets/search-index.js` | Generated by `tools/build_search_index.py`; never edit it by hand |
| `book/sitemap.xml`, `book/robots.txt` | Generated by `tools/build_site_meta.py`, which also writes the marked metadata block in each page's `head`; never edit them by hand |
| `labs/` | One folder per lab, with its code, tests and README. `labs/common/llm.py` is the model adapter every lab shares |
| `labs/notebooks/src/` | The notebook sources. The `.ipynb` files in `labs/notebooks/` are generated from them |
| `tools/` | The local server, the checks and the generators; `tools/tests/` holds the tests for the progress tracker, the footer and Ask AI |

The README's [Layout](README.md#layout) table lists the rest.

## Set up on your computer

You need git and Python 3.10 or newer. The progress tracker's tests also need Node.js (the
checks on GitHub use Node 20).

    git clone https://github.com/YOUR-NAME/build-ai-handbook.git   # your fork
    cd build-ai-handbook
    python3 -m venv .venv
    source .venv/bin/activate          # Windows: .venv\Scripts\activate
    python -m pip install -r labs/requirements.txt

To read the book as you change it, run `python3 tools/serve.py` and open
<http://127.0.0.1:8765/>.

You do not need an API key to contribute. The labs' `fake` backend gives scripted replies,
needs nothing and costs nothing, and the tests always use it. With neither `LLM_BACKEND`
nor a key set, the labs use it and say so.

"Open in Codespaces" on any lab page gives you a machine with Python and the lab
requirements already installed.

## Make a change

1. **Fork the repository**, or create a branch if you have write access. `main` is
   protected, so every change, the maintainer's included, goes through a pull request.
2. **Name the branch for what it holds**, for example `fix-softmax-example`.
3. **Make one logical change per commit**, with a
   [Conventional Commits](https://www.conventionalcommits.org/) subject: `docs:`,
   `fix(labs):`, `feat(book):`, `test:`, `ci:`. The subject says what changed, for
   example `fix(labs): Lab 0's cost table quotes the capstone's own estimate`. The body says
   why, and what you checked.
4. **Regenerate generated files in the same commit** as the change that alters them: the
   search index after a heading changes, a page's metadata after its main heading or lead
   paragraph changes, a notebook after its source changes.
5. **Open one pull request per goal.** A typo fix and a new section are two pull requests.
   The template asks what changed, why, and which checks you ran.

The same checks run on every pull request (`.github/workflows/check.yml`). A red check
names the step that failed.

## Checks to run before a pull request

Run these from the repository root. They use only the Python standard library or Node's
built-in test runner:

    python3 tools/check_links.py                 # every internal link and #id resolves
    python3 tools/check_book.py                  # reading order, page structure, ids, paths, addresses
    python3 tools/build_search_index.py --check  # the search index is up to date
    python3 tools/build_site_meta.py --check     # page heads, sitemap.xml and robots.txt are up to date
    python3 tools/build_notebooks.py --check     # notebooks match their sources; launch links
    node --test tools/tests/*.test.js            # the progress tracker, the footer's links, the Ask AI request

If a check says the search index, the page metadata or a notebook is out of date, run
`python3 tools/build_search_index.py`, `python3 tools/build_site_meta.py` or
`python3 tools/build_notebooks.py` without `--check`, then commit the result with your
change.

If you changed a lab, `labs/common/` or a notebook source, also run the lab tests and the
notebooks. They need a few more packages:

    python -m pip install -r labs/06-mcp-server/requirements.txt "nbclient>=0.10" "nbformat>=5.10" "ipykernel>=6.29"
    (cd labs && python -m pytest)                # every lab's tests, on the fake backend
    python tools/run_notebooks.py                # every notebook runs on the fake backend

The tests in `tools/tests/browser.test.js` drive the real pages in headless Chromium (the
progress tracker, the footer and the Ask AI panel, with a stand-in for the Anthropic API so
they never call it), and are skipped when playwright is missing. If you changed
`book/assets/progress.js`, `book/assets/handbook.js` or `book/progress.html`, run them the
way the checks on GitHub do, with playwright installed in a folder outside the repository:

    npm install --no-save --prefix /tmp/pw playwright@1.49.0
    /tmp/pw/node_modules/.bin/playwright install chromium
    NODE_PATH=/tmp/pw/node_modules REQUIRE_BROWSER=1 node --test tools/tests/browser.test.js

## Writing for the book

The section "Conventions" in `book/reading.html` is the reader's side of these rules. Read
it, and two neighbouring pages, before you write.

- **Plain English.** British spelling (normalise, behaviour), short sentences, active
  voice, they/them for people. Say what a thing does, what it costs and how you know. No
  hype, no superlatives, no exclamation marks.
- **Numbers before symbols.** Every formula comes after a worked example with real
  numbers. Formulas are plain HTML, written with the `formula` and `frac` classes and
  `<var>`, as in `book/reading.html`.
- **Four kinds of box**, and only these, written as
  `<div class="callout why"><span class="title">Why it matters</span><p>…</p></div>`:
  `why` (the problem an idea solves), `warn` (a common mistake or a rule not to break),
  `note` (a side remark, and the maths chapters' "Try it" exercises) and `build` (sends
  the reader to the lab where they build the idea). `check_book.py` rejects any other kind.
- **Name files from the repository root**, in `<code class="path">`, such as
  `labs/03-rag/rag.py` or `book/assets/handbook.js`. `check_book.py` checks that every
  such path under `book/`, `labs/` and `tools/` exists. Name the function or class that
  matters, and never cite line numbers: they change with every edit.
- **Give every `h2` and `h3` an `id`**, unique on its page. Search links to these ids, so
  rename one only when you must, and fix the links that `check_links.py` reports.
- **Checklist ids.** A lab's steps end in `<ul class="checklist">`, one
  `<li data-check="page-name:step">` per step, where `page-name` is the file name without
  `.html`. The ids are unique across the book. Readers' ticks are stored against them, so
  renaming one loses the ticks readers already have for that step.
- **Self-checks.** A chapter ends with three or four questions in
  `<section class="selfcheck">`, each a `<details>` whose answer opens on click.
- **Widgets** live in `book/assets/widgets/`, one file per widget, loaded only by the pages
  that use it. They use the helpers in `book/assets/handbook.js` (`HB.el`, `HB.svg`,
  `HB.fmt`), read colours from the CSS variables so they follow the light and dark themes,
  and say plainly when they use toy data.
- **Nothing from another site.** The website allows scripts, styles, fonts and images from
  its own address only (see `vercel.json`), and the pages need no network. Do not add a
  script, font, image or embed from elsewhere. Plain links to other sites are fine;
  open them in a new tab with `target="_blank" rel="noopener noreferrer"`, as the pages do.
  The one outside connection is Ask AI's call to `https://api.anthropic.com` with the
  reader's own key: `connect-src` in `vercel.json` allows it, and `tools/check_book.py`
  fails if the policy names any other site.

### Adding a page

1. Copy a neighbouring page. Change its title, kicker, lead and body, and keep the `head`,
   the sidebar `nav` and the pager `nav` as they are. The title ends with
   `&middot; Build AI handbook`.
2. Add the page to the `BOOK` list at the top of `book/assets/handbook.js`, on one line
   like its neighbours, with the keys in the order `file`, `part`, `n` (chapters only),
   `title`.
3. Add a card for it to the contents in `book/index.html`.
4. Run `python3 tools/build_search_index.py` and `python3 tools/build_site_meta.py`, then
   the checks above.

Commit the page, the `BOOK` list, the contents, the search index and the files
`build_site_meta.py` wrote together. Run the
search index again whenever you add or rename a heading, a checklist step or a glossary
entry.

## Working on the labs

- **A lab has three parts that must agree:** its folder in `labs/` (code, tests and
  README), its page in `book/`, and its notebook source in `labs/notebooks/src/`. A change
  to what a lab does usually touches all three.
- **Tests use the fake backend.** `labs/conftest.py` sets `LLM_BACKEND=fake` for every
  test, so a test must pass with no key and no network. To script the model's replies in
  a test, use `llm.fake.script(...)`, as the existing tests do.
- **Never commit a key**, a `.env` file or any file that holds a key. Keys belong in your
  shell, in Colab's Secrets panel or in Codespaces secrets. git ignores `.env`, but check
  `git status` before you commit.
- **Notebooks are generated.** Edit the source in `labs/notebooks/src/`, run
  `python3 tools/build_notebooks.py`, and commit the source and the `.ipynb` together.
  Never edit an `.ipynb` file by hand. A source is a plain Python file split into cells by
  lines that start with `# %%`; the generator adds the same setup cells to every notebook.
- **Costs stay true.** Every lab page says what a run costs on Claude and how that was
  worked out. If your change alters the prompts, the default model or the number of calls,
  update that figure.
- **Dependencies.** The numbered labs need only what `labs/requirements.txt` lists. Propose
  a new package in an issue first. If it is agreed, add it to `binder/requirements.txt` as
  well: `build_notebooks.py --check` fails when Binder's list misses one the labs need.

## Licensing of contributions

The project has two licences, and contributions are accepted under the same ones:

- the text of the book (the prose, figures and diagrams of the pages in `book/`) is under
  Creative Commons Attribution 4.0 (CC BY 4.0), in `LICENSE-TEXT`;
- the code (`labs/`, `tools/`, `book/assets/`, the notebooks and the code samples in the
  pages) is under the MIT License, in `LICENSE`.

By opening a pull request, you agree that your contribution is licensed under these terms.
Send only work you wrote or have the right to share under them. When you draw on someone
else's work, link to it and credit it, as the pages' "Further reading" lists do.
