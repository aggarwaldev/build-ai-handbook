Lab 4: measure your retrieval

Score the retriever you built in Lab 3 on 25 labelled questions, with the ranking metrics of chapter 26. Add a keyword retriever, BM25, and fuse the two; compare chunk sizes; and put an error bar on every score, so you can see how much 25 questions can tell you. No model is called, so the lab costs nothing and gives the same numbers on every run.

Why build it

In Lab 3, one question missed and a dozen others worked. That is an anecdote, not a measurement. Every change you might make next, a smaller chunk, a different retriever, headings in or out, fixes some questions and breaks others. A small labelled set and a few metrics turn "it feels better" into a number, and the error bar tells you whether the number moved more than chance would move it.

What you will build

One file, labs/04-retrieval-eval/retrieval_eval.py, and a question set, questions.jsonl. It imports Lab 3's rag module for the chunks, the tokens and the TF-IDF index.

Step 1: labelled questions

For each question, write down which passages answer it. That is the whole labelling job, and it is the expensive part (chapter 26). Each line of questions.jsonl is one question:

{"id": "q13", "kind": "direct", "question": "Do children pay late charges?", "relevant": ["fines#late-returns", "membership#childrens-cards"]}
{"id": "q14", "kind": "paraphrase", "question": "How long can I keep a book?", "relevant": ["loans#loan-periods"]}

Three choices matter:

  • Labels name sections, not chunks. A section keeps its id whatever the chunk size, so the same labels score a 20-word index and a 120-word one. A chunk counts as relevant when its section is.
  • Two kinds of question. 13 are direct: they use the pages' own words, as people do after reading the site. 12 are paraphrases, written the way people actually ask: "My nan is hard of hearing. Is there anything to help her at the counter?" shares one word with the section that answers it. Scoring the kinds separately shows what a word-based retriever cannot do.
  • Some questions have two right answers. q13 and q22 are each answered by two sections, so recall@3 can be ½.

A label that names a section which does not exist would quietly score as a miss forever. test_every_label_names_a_real_section checks every label against Lab 3's chunks, and fails the moment a heading is renamed.

Step 2: the metrics

Each metric takes a ranked list of section ids, best first, and the set of relevant ones (chapter 26):

def hit_at_k(ranked, relevant, k):
    return 1.0 if any(r in relevant for r in ranked[:k]) else 0.0

def recall_at_k(ranked, relevant, k):
    return sum(r in relevant for r in ranked[:k]) / len(relevant)

def reciprocal_rank(ranked, relevant):
    for rank, r in enumerate(ranked, start=1):
        if r in relevant:
            return 1.0 / rank
    return 0.0

def ndcg_at_k(ranked, relevant, k):
    dcg = sum(1 / math.log2(rank + 1) for rank, r in enumerate(ranked[:k], start=1) if r in relevant)
    ideal = sum(1 / math.log2(rank + 1) for rank in range(1, min(len(relevant), k) + 1))
    return dcg / ideal

The tests use chapter 26's worked examples as fixtures. For relevance 0 1 0 1 0 with three relevant passages, they expect recall@5 = 0.667, a reciprocal rank of 0.5 and nDCG@5 = 0.498; for first relevant ranks of 1, 3, none and 2, an MRR of 0.458. If you change a metric and a test fails, compare your code with the hand calculation in the chapter. Every relevant section counts with a gain of 1, because the labels have no grades. precision_at_k is in the file too, but not in the table: with one relevant section per question, precision@3 can never exceed ⅓, so it says little here.

Step 3: a keyword retriever, BM25

TF-IDF and BM25 both count shared words, but BM25 gives repeated words diminishing returns and corrects for passage length (chapter 25):

def scores(self, query):
    words = self.tokenize(query)
    out = []
    for counts, length in zip(self.counts, self.lengths):
        norm = self.k1 * (1 - self.b + self.b * length / self.avglen)
        out.append(sum(self.idf[w] * counts[w] * (self.k1 + 1) / (counts[w] + norm)
                       for w in words if counts[w]))
    return out

with idf = ln(1 + (N − n + 0.5) / (n + 0.5)), k1 = 1.2 and b = 0.75. It uses Lab 3's tokens, so both retrievers see the same words. test_bm25_on_the_chapter_25_example feeds it the chapter's three documents with plain whitespace splitting and expects the chapter's scores for "fixed deposit": 0.894, 0.482 and 0.482.

Step 4: fuse the two

TF-IDF scores are cosines between 0 and 1; BM25 scores have no upper limit. Rather than rescale them, reciprocal rank fusion ignores the scores and adds 1 / (60 + rank) from each list (chapter 25):

def rrf(rankings, k=60):
    total = defaultdict(float)
    for ranking in rankings:
        for rank, item in enumerate(ranking, start=1):
            total[item] += 1 / (k + rank)
    return sorted(total.items(), key=lambda kv: -kv[1])

The tests check the chapter's worked numbers: a passage 1st by vectors and 3rd by keywords scores 1/61 + 1/63 = 0.03227, and loses to one 2nd and 1st, at 0.03252.

Step 5: from chunks to sections

Each retriever returns its top 10 chunks that share at least one word with the question. sections replaces each chunk by its section and keeps each section once, at its best rank. Without that, two pieces of the same long section would fill two of the top three places and could count twice. A question whose relevant section is not in the top 10 gets a reciprocal rank of 0, so the MRR here is MRR@10.

Step 6: how sure can you be?

Twenty-five questions are a small sample of the questions people will ask. If you had written 25 different ones, every score would come out a little different. The bootstrap estimates by how much, from the 25 you have. Draw 25 questions from your set at random, with replacement, so some appear twice and some not at all, and average their reciprocal ranks. Do that 2,000 times. Sort the 2,000 averages and drop the lowest 50 and the highest 50: what remains spans the middle 95%, a confidence interval for the MRR.

def bootstrap_ci(values, n=2000, seed=0, level=0.95):
    rng = random.Random(seed)
    m = len(values)
    means = sorted(mean([values[rng.randrange(m)] for _ in range(m)]) for _ in range(n))
    tail = (1 - level) / 2
    return means[int(n * tail)], means[int(n * (1 - tail)) - 1]

Comparing two retrievers on the same questions is sharper than comparing their two intervals, because questions differ in difficulty far more than retrievers do (chapter 26). paired_difference takes the difference in reciprocal rank question by question and bootstraps that list. If its interval contains 0, these questions cannot tell the two apart. The seed is fixed, so the intervals below come out the same on every run; change --seed and they move in the second decimal place.

Reading the table

  • The hit rate at 3 is 0.80 for Lab 3's own setup (TF-IDF, 120 words): 20 of 25 questions have a right section in the top 3, the passages rag.py sends by default. The five misses are what a model would see as the wrong passages.
  • Direct questions are solved; paraphrases are not. Every retriever finds all 13 direct questions in its top 3, and only 7 to 9 of the 12 paraphrases. All three retrievers count shared words, so a question in other words defeats them. This is the gap a trained embedding model is for.
  • BM25 looks best, and the evidence is thin. At 120 words its hit@3 is 0.88 against 0.80, a difference of two questions (q14 and q16, both third for BM25 and fourth for TF-IDF). The paired MRR difference is +0.027 with an interval from −0.007 to +0.077: it contains 0, so these 25 questions cannot show that BM25 is better.
  • Fusion did not help. RRF scores at or below its better input. Both lists fail on the same paraphrases, and fusion cannot add a passage that neither list ranks highly. Chapter 25 found the same when both lists were weak. Fusion pays off when the two retrievers fail on different questions, such as keywords and a trained embedding model.
  • Smaller chunks did not help either. At 20 words, TF-IDF's hit@1 falls from 0.68 to 0.64 and its MRR from 0.77 to 0.73. A 20-word window loses words that the rest of its section supplied.
  • Every MRR interval is 0.26 to 0.30 wide. TF-IDF's MRR of 0.77 could plausibly be anything from 0.63 to 0.90 on another 25 questions of the same kind. Differences of 0.03 between rows are well inside that.

What it costs

Nothing. The report makes no model call: it counts words, multiplies small matrices and resamples lists, and finishes in well under a second on a laptop. test_the_report_runs_without_calling_a_model replaces the adapter's chat with a function that fails, and the report still runs. With --ollama, the embeddings come from a model on your own computer, which is also free.

Experiments

  1. Headings out. Run with --no-headings. In the run here, at 120 words, TF-IDF's hit@1 fell from 0.68 to 0.60 and its MRR from 0.77 to 0.73, while its hit@3 rose from 0.80 to 0.84 and its paraphrase hit@3 from 0.58 to 0.75. Headings helped questions that use the pages' words (q10, "Local Studies room", went from 8th to 3rd with them) and hurt paraphrases that share a word with another page's heading: q14 went from 2nd without them to 4th with them, lured by "How long we keep your account". Which metric decides depends on how many passages you send.
  2. Overlap. Run --sizes 20 40 --overlap 10. In the run here, at 20 words TF-IDF's hit@3 rose from 0.80 to 0.84 and its MRR from 0.73 to 0.77, the same MRR as the 120-word index: overlap gave the small windows back some of the words their neighbours held. It cost 187 chunks instead of 137.
  3. Pair the heading runs. The report pairs retrievers within one run. Write a short script that runs evaluate twice, with heading paths on and off, and passes the two lists of reciprocal ranks to paired_difference. Is the MRR change in experiment 1 bigger than chance?
  4. More questions. Write 25 more questions, half of them paraphrases, or better, ask someone who has not read the pages to write them and label them yourself. Watch the intervals narrow. Four times as many questions should roughly halve their width.
  5. Tune BM25. Set b=0 to turn off the length correction, or k1=0 to make one occurrence count as much as ten. Which questions change rank?
  6. Change the fusion constant. Try rrf(..., k=1). With a small constant, first place in either list dominates. Does it help or hurt here?
  7. Real embeddings. With Ollama running and nomic-embed-text pulled, add --ollama. Watch the paraphrase column: if a trained model closes the gap, then fusing it with BM25, the rrf-ollama row, is where fusion can finally help. These runs were not made for this page; your numbers are your own.

Going further

  • Graded labels. Mark each relevant section 2 (answers it) or 1 (related), and use the grade as the gain in nDCG (chapter 26). It is the only metric here that can use them.
  • Questions with no answer. Retrieval metrics are undefined when nothing is relevant, so score those questions on the answer instead: does the model say the passages do not answer it?
  • The generation half. Good retrieval does not guarantee a good answer. Lab 8 builds a judge for faithfulness and citation support, and checks it against people.
  • Guard against regressions. Run this report in your test suite and fail the build if hit@3 drops below a floor you choose. With 25 questions, set the floor a few questions below today's score, or ordinary noise will fail it.

Self-check

BM25 scores hit@3 0.88 and TF-IDF 0.80. Is BM25 the better retriever for these pages?

Not shown. The gap is two questions out of 25, and the paired MRR difference has an interval from −0.007 to +0.077, which contains 0. It may be better; these questions cannot tell.

Why do all three retrievers find every direct question and miss several paraphrases?

All three score shared words. A direct question uses the page's words; a paraphrase uses others ("shut" for "close", "granddaughter" for "child"), and word counting cannot connect them. A trained embedding model can.

Why did fusing TF-IDF and BM25 not help?

They fail on the same questions, because both count the same words. Fusion can only promote a passage that at least one list ranks highly. It helps when the two retrievers make different mistakes.

Why resample the questions, not the chunks, in the bootstrap?

The questions are the sample: they stand in for all the questions people will ask. The chunks are fixed. The interval answers "how different would the score be with other questions like these?"

Why turn chunks into sections, once each, before scoring?

Labels name sections. Without the merge, two pieces of one section could take two of the top three places and count twice in recall, and a long section would look more relevant than a short one just for being cut into more pieces.
